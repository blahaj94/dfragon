# 인증·탈퇴 운영 구성

## 적용 범위와 이전 결정

MVP는 한 운영자가 관리하는 단일 API와 auth PostgreSQL 구성으로 시작할 수 있다. 장비 3대, 별도 관리 인원, 전용 witness 서비스와 전체 장애 시험을 로그인·일반 기능 배포의 선행 조건으로 요구하지 않는다. [PR #132의 이전 운영 설계](https://github.com/blahaj94/ldb/pull/132)와 [D1–D5 승인 이력](https://github.com/blahaj94/ldb/pull/72)은 보존하며, 장비·역할·검증의 현재 기준은 이 문서를 따른다. 이 변경은 채택 범위를 명시한 PR의 사용자 merge 후 적용한다.

탈퇴의 확정·재인증·삭제·보관 의미는 [탈퇴 계약](../rules/auth-withdrawal-proposal.md)을 유지한다. 이 문서는 구현 완료나 실제 운영 실행 허가를 뜻하지 않는다. 현재 구현·환경에 없는 기능을 동작한다고 표시하지 않는다.

## MVP 구성과 책임

- 단일 API process와 DB를 같은 서버에서 운영할 수 있다. 장비 수와 서비스 수는 실제 부하·복구 요구에 맞춰 늘린다. 같은 host의 volume 분리를 물리 장애 격리로 설명하지 않는다.
- 탈퇴를 구현하면 D1의 취소 불가 확정점인 durable 삭제 journal과 이전 writer 차단을 유지한다. Journal·현재 checkpoint·inventory는 auth DB의 복원 대상과 구분된 저장·권한 경계를 가진다. 같은 host의 별도 DB·volume도 가능하며, host 전체 손실이나 공동 rollback 뒤 복구를 보장하지 않는다.
- 별도 witness와 분산 control 조정 process는 기본 필수 구성이 아니다. 검증된 백업 공개 복원을 제공할 때 필요한 최신성·rollback 방지 수단을 선택한다. 단순 checksum이나 같은 snapshot 안의 journal/checkpoint로 최신성을 증명할 수 있다고 가정하지 않는다.
- 운영자 한 명이 배포·Migration·backup·복구·secret 관리를 겸할 수 있다. 실행 자격은 목적별 최소 권한으로 나누고 API에 DDL·host 관리자·backup 복호화 권한을 부여하지 않는다. 같은 사람의 계정 분리를 독립 관리자에 의한 침해 방지로 설명하지 않는다.
- 내부 DB 연결은 외부 공개를 제한하고 선택 환경의 신원·암호화·접근 제어를 적용한다. Secret은 source·image·dump·일반 log에 넣지 않는다. 기존 API 설정 입력과 명시 Migration은 [auth-runtime.md](../rules/auth-runtime.md)를 따른다.
- 요청 범위의 통상적인 도구 선택은 [개발 흐름](../rules/agent-workflow.md#판단과-권한)을 따른다. 관리형 저장·백업 서비스도 비교 대상에서 배제하지 않으며, 실제 도입의 비용·개인정보 처리·운영 책임과 외부 전송은 사용자 결정 범위다. 새로운 서비스를 자동 구독하거나 데이터를 전송하지 않는다.

## 백업과 공개 복원의 분리

백업 생성과 백업에서 복원한 auth DB를 사용자에게 다시 공개하는 것은 별개다. MVP에서는 백업 공개 복원을 제공하지 않는 상태로 기능을 개발·배포할 수 있다. 복원 기능이 필요해질 때만 해당 저장·운영 경계를 구현하고 [복원 검증 기준](auth-operations-validation-proposal.md)을 적용한다. 그 전에는 복원된 DB를 ingress에 연결하거나 기존 데이터의 복구 가능성·RPO/RTO를 약속하지 않는다. 복원 기능 미제공과 그에 따른 데이터 손실·서비스 중단 가능성은 배포 결과에 명시한다.

백업을 만들면 D5의 최대 성공본 7개·snapshot 나이 7일 상한, 암호화·사본 목록과 만료 삭제를 적용한다. 복원하지 않는다는 이유로 오래된 사본이나 삭제 회원 데이터를 계속 보관하지 않는다. 백업 기능을 구현하지 않는 동안 빈 inventory를 만들기 위한 서비스·장비를 구축하지 않는다.

공개 복원을 켜려면 현재까지 누락 없는 삭제 journal, auth 복원 범위 밖 최신 checkpoint의 rollback 방지 근거, 사본의 origin·나이와 이전 writer 차단을 확인해야 한다. 이를 확인할 수 없는 단일 host snapshot·공동 rollback·journal 손실에서는 기존 auth를 복원해 공개하지 않는다. 장비 3대가 있다는 사실만으로 이 조건을 통과하지 않는다.

## 내구성·삭제·시각

Durable 성공은 선택한 저장소의 transaction commit·flush 계약과 오류 처리로 판단한다. 메모리 ack나 비동기 미확정 write를 탈퇴 확정으로 사용하지 않는다. 단일 writer·잠금·멱등성·재시작 판정을 구현하고, 실제 변경에 필요한 crash 사례를 선택한다. 물리 정전·disk clone·전체 network partition 조합 시험은 일반 기능의 출시 선행 조건이 아니다. 실행하지 않은 물리 내구성이나 공동 손실 복구를 보장했다고 표시하지 않는다.

삭제·보관 기한과 장애 잔여는 D4/D5를 유지한다. 매번 다른 물리 매체로 전체 복사·sanitize하는 한 가지 구현을 강제하지 않는다. 선택 저장소에서 확인 가능한 삭제·compaction 또는 해당 데이터와 모든 복구키 사본의 암호학적 폐기 등으로 계약을 충족한다. 단순 unlink·SQL DELETE를 WAL·snapshot·복제본까지 제거했다는 증거로 확대하지 않는다. 방법을 확인하지 못하면 삭제 완료로 표시하지 않고 D4의 최소 격리·지연 안내·복구 후 우선 삭제를 적용한다. 상시 충족할 수 없는 보관 방식을 장애 예외로 정당화하지 않는다.

임시 dump·restore scratch도 비민감 소유 식별자와 종료 정리 책임을 두되 job마다 물리 disk 확보를 요구하지 않는다. 다른 유효 사본까지 파괴하는 공유 key 삭제나 광역 prune은 하지 않는다. Journal의 개인정보와 보관 기한을 유지하며 별도 복구 기능이 없어도 완료된 삭제 기록을 무기한 보관하지 않는다.

시각·key·cleanup은 기존 TTL·만료·교체 계약을 따른다. 실제 시각이 불명확하면 영향받는 만료·삭제·복원 판정을 보류하며, 모든 시계 장애를 미리 재현하는 시험을 선행 작업으로 추가하지 않는다.

## 운영 확인과 후속 작업

배포에서는 선택 환경의 시작·종료, 필수 설정, 접근 권한, 명시 Migration과 이번 기능의 정상·중요 실패 흐름을 확인한다. 탈퇴를 제공할 때는 확정 intent·재개·삭제와 보관을 검증한다. 공개 복원을 제공할 때만 복원 대상 밖 기록·옛 자격 폐기·삭제 재적용·재개 조건을 검증한다. 미구현 기능의 운영 matrix를 다른 기능의 완료 조건으로 붙이지 않는다.

과거 3대 구성의 B/C 예약 protocol, 독립 관리자와 매체 교체 절차는 Git 이력의 비교 설계다. 현재 요청에서 그 보장이 필요하고 채택했을 때만 구체화한다. 현재 구성·복원 제공 여부·검증 결과와 남은 한계는 관련 배포 PR 또는 운영 기록 한 곳에 짧게 남긴다.
