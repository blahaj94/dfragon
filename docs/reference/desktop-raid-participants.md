# 공대원창 검출과 닉네임 크롭

12행 공대 상세 창에서 닉네임 원본 크롭과 행별 영역을 반환하는 공통 함수입니다. [기존 파티참가인원 창](desktop-party-participants.md)의 네 고정 슬롯과 달리, 공대원이 나가면 아래 행이 위로 당겨집니다. 행 번호는 한 프레임의 화면 위치이며 캐릭터의 식별자가 아닙니다.

## 범위

- 같은 모양의 12행 공대창을 대상으로 하며 실제 참가자는 12명보다 적을 수 있습니다. 별도 8인 레이드 레이아웃은 포함하지 않습니다.
- 호출자가 게임 client와 기준 이미지를 RGBA로 디코딩해 전달합니다. 함수 내부에서 화면 캡처, 파일 접근, 네트워크 요청이나 앱 상태 변경을 하지 않습니다.
- 닉네임은 OCR을 실행하지 않고 원본 픽셀을 복사합니다. 창을 찾지 못하거나 검출이 모호하면 정상 크롭으로 반환하지 않습니다.
- R/Y/G·싱글 구분과 장비 점수 판독도 객체 반환에 한정합니다. 점수는 쉼표·소수점·K를 포함한 화면 문자열을 유지하며 숫자로 환산하지 않습니다. 판독값을 정답으로 간주하지 않습니다.
- Desktop의 공대원창 크롭 탭이 닉네임 검출 함수를 사용합니다. `raid` 수집 종류로 1~12행을 저장하고 OCR 자료실 전송과 기존 정답 입력·평가에 연결합니다. HUD·파티원창의 네 행 제한과 메타데이터 함수의 반환 범위는 유지합니다.

## 행과 판독값

닉네임 크롭은 참가한 행에서만 반환하며 빈 행도 화면 위치를 유지해 표현합니다. 프레임이 바뀔 때 이전 행의 닉네임이나 메타데이터를 재사용하지 않습니다. R/Y/G·싱글은 해당 행의 실제 표식을 읽으며 행 번호로 파티를 추정하지 않습니다.

참가 여부와 각 필드의 판독 성공은 별개입니다. 파티 표식이나 점수를 판독하지 못해도 닉네임 크롭을 버리지 않습니다. 점수 원문 `1000.4K`에서 화면에 표시되지 않은 실제 점수를 복원하거나 정답을 추측하지 않습니다.

## 공대창 API와 좌표

`detectDNFRaidParticipantWindow(frame, headingTemplate)`은 `found`일 때 `window`, `scale`, `matchScore`와 12개의 `rows`를 반환합니다. `cropDNFRaidParticipantNicknames`는 같은 입력에서 각 행의 `nicknameCrop`을 추가합니다. 참가 행의 크롭은 독립 RGBA 복사본이고 빈 행은 `null`입니다. 실패 결과는 기존 파티원창과 같은 `not-found`, `ambiguous`, `search-limit`으로 구분합니다.

두 입력은 `{ width, height, rgba }`이며 `rgba`는 행 우선의 premultiply하지 않은 `Uint8Array | Uint8ClampedArray`입니다. 정확히 `width × height × 4`바이트를 요구하며 원본 alpha를 보존합니다. 게임 client의 정수 크기 범위는 1067×600~1920×1080입니다. 모든 중간 크기를 실제 게임에서 검증한 것은 아닙니다.

기준 헤더는 UI 0%의 `423 × 18` RGBA로, 파티·레벨·장비 점수·캐릭터 이름·직업명 및 오른쪽 빈 열의 배경과 구분선을 포함합니다. 호출자가 기준 이미지를 보관·디코딩하며 라이브러리에 게임 이미지나 플레이어 데이터를 포함하지 않습니다. 입력 크기·바이트 길이가 잘못됐거나 기준 헤더에 대비가 없으면 `RangeError`를 던집니다.

다음은 헤더 좌상단을 원점으로 한 UI 0% 관측값입니다. 오른쪽·아래쪽 경계는 포함하지 않습니다.

| 대상 | 기준 좌표 |
| --- | --- |
| 팝업 외곽 | 왼쪽 −15, 위 −68, 오른쪽 450, 아래 324: `465 × 392` |
| 빨간 기준 아이콘 중심 | `(405, −10)` |
| 행 시작 | `y = 18 + 21 × (row − 1)` |
| 닉네임 | `x = 182..268`, `y = 행 시작 + 3..20`: `86 × 17` |
| 파티 표식 | `x = 3..45`, `y = 행 시작 + 2..19`: `42 × 17` |
| 장비 점수 | `x = 106..181`, `y = 행 시작 + 3..20`: `75 × 17` |

닉네임·파티·점수 사각형은 입력 client 기준 좌표입니다. 배율을 적용한 각 모서리를 기존 파티원창과 같은 ties-to-even 규칙으로 반올림하며, 행 간격을 먼저 반올림해 누적하지 않습니다.

검출은 기존 빨간 연결 영역·헤더 정규화 상관 함수를 재사용하며 헤더 치수와 아이콘 위치를 공대창에 맞춥니다. 팝업 전체 경계와 12행 구분선으로 후보를 먼저 좁히고 초상화·레벨·역할 아이콘 근거로 참가 여부를 판단합니다. 후보 128개와 프레임당 비교 표본 64,000,000개의 기존 탐색 한도를 유지하며, 한도를 넘으면 앞에서 찾은 후보도 부분 성공으로 반환하지 않습니다.

## 파티·점수 판독 API

`readDNFRaidParticipantMetadata(frame, rows, templates)`에 검출 결과의 행과 같은 프레임을 전달하면 행별 `{ row, party, equipmentScoreText }`를 반환합니다. `party`는 `R`, `Y`, `G`, `싱글` 중 하나이며, 각 필드의 미판독과 빈 행은 `null`입니다. 빈 행과 참가 행의 미판독은 원래 행의 `occupied`로 구분합니다. 닉네임 크롭과 판독 결과를 합치는 일은 호출자가 담당합니다.

`DNFRaidMetadataTemplates`는 호출자가 준비하는 다음 기준 이미지입니다. 라이브러리가 기준 데이터를 내려받거나 모델을 학습하지 않습니다.

- `parties`: `{ party, image }` 배열. UI 0%의 표식 영역 전체인 `42 × 17` RGBA를 사용합니다.
- `equipmentScoreGlyphs`: `{ character, image }` 배열. 문자 하나의 폭 1~16, 높이 17 RGBA를 사용하며 `0`~`9`, 쉼표, 소수점, 대문자 `K`를 구분합니다. 문자 전체 획과 점수 영역 안의 세로 위치를 보존해야 하며 가로 여백은 허용합니다.

판독은 필드의 사본을 기준 크기로 맞춰 수행하며 원본을 바꾸지 않습니다. 파티는 색상과 표식 패턴을 비교하고, 점수는 국소 대비로 글자 획을 분리해 기준 글자와 비교합니다. 기준 이미지·행 번호·영역 경계는 검증하며 잘못된 입력은 `RangeError`로 거절합니다. 기준 글자에 없는 문자나 불확실한 필드를 임의의 숫자·파티로 채우지 않습니다.

## 검증 자료와 한계

제공된 로컬 스크린샷은 1067×600 JPEG 8장입니다. 전체 12명인 화면 네 장과 각각 10·8·7·9명이 있는 화면을 포함하며, 총 참가 행은 82개입니다. 실제 플레이어 데이터와 원본 화면은 저장소·CI에 포함하지 않습니다.

공개 크롭 함수에서 8장 모두 창을 찾았으며 82개의 참가 행과 나머지 빈 행을 기대대로 반환했습니다. 모든 닉네임 영역은 실측 좌표와 일치했고 크롭 바이트·alpha·입력 버퍼 보존을 확인했습니다. 전체 크롭을 확대해 닉네임 글자 잘림이 없는 것도 확인했습니다. 최소 해상도 한 화면에서 기준 헤더를 추출했으므로 8장 전체가 독립 검증 표본은 아닙니다.

macOS 로컬 Node의 별도 확인에서는 프레임당 약 31~45ms였습니다. Windows 캡처·렌더러 전달을 포함하지 않는 관측값이며 일반적인 검출 정확도나 실행 시간 보장은 아닙니다.

Windows 10에서 게임과 같은 세션의 관리자 권한 앱으로 실제 GDI 캡처와 물리 키보드 Print Screen 저장을 확인했습니다. 1067×600·검출 배율 1.0에서 `86 × 17` PNG 12장, 1920×1080·검출 배율 1.8에서 `154 × 30~31` PNG 12장이 저장됐습니다. 두 번 모두 `raid` 종류와 1~12행, 원본 client 크기·검출 배율이 보존됐으며 미작성 정답으로 기존 목록에 연결됐습니다. 이 배율은 함수의 검출값이며 게임 설정의 UI 크기 백분율을 확인한 값은 아닙니다.

확대된 12명 공대창의 연속 8프레임에서는 원본의 참가 행 96개와 검출 결과가 모두 일치했습니다. 각 미리보기 크롭은 같은 프레임의 팝업 원본 픽셀과 일치했습니다. 공대 전환 중 앞서 10행이 반환된 순간은 당시 원본을 확보하지 못했으므로 실제 인원 변동인지 오검출인지 확정하지 않았습니다. 원본을 대조한 이후 표본에서는 누락이 재현되지 않았습니다. 실제 게임의 인원·공대 변경과 강조 효과 때문에 서로 다른 시각의 저장 이미지와 미리보기가 같다고 가정하지 않습니다.

Playwright로 Windows의 실제 renderer에서 저장된 24개 조회, 12행 선택과 원본 크기·배율 표시, 정답 입력 가능 상태를 확인했습니다. 정답 입력 탭으로 이동한 뒤 수집이 해제됐고 실제 탑재 OCR 모델로 선택 이미지 평가 1건이 완료됐습니다. 이 이미지는 정답 미입력 상태이므로 OCR 정확도를 채점한 결과는 아닙니다.

이 확인은 같은 소스의 일반 main 빌드와 CI Windows 실행 라이브러리를 사용한 독립 로컬 프로필에서 진행했습니다. 배포 API를 연결하지 않은 비로그인 검증이며 실제 설치본이나 OCR 서버 전송 성공을 뜻하지 않습니다.

같은 82행에서 파티 표식과 점수 문자열을 판독했고 원본 확대 이미지와 대조했습니다. 참가자가 없는 14행은 판독값이 모두 `null`이었습니다. 기준 표식·숫자도 제공 자료에서 추출했으므로 이 결과를 독립 데이터셋의 정확도로 해석하지 않습니다.

[공대창 합성 테스트](../../packages/lib/test/dnf-raid-participants.test.mjs)는 이동·배율·인원 감소·빈 행·원본 픽셀 보존·모호 후보·잘린 창·탐색 한도를 확인합니다. [메타데이터 합성 테스트](../../packages/lib/test/dnf-raid-metadata.test.mjs)는 R/Y/G·싱글, 색상이 다른 점수, 쉼표·소수점·K, 확대, 미판독·모호한 기준 이미지, 잘못된 입력을 확인합니다. 공통 매칭 함수를 사용하는 기존 네 행 파티원창 테스트도 함께 통과했습니다.

제공 화면에는 K 단위 점수가 없습니다. K 표기의 합성 검증과 실제 게임 화면 판독은 구분합니다. 위 두 client 크기·검출 배율 이외의 실제 조합, 별도 8인 레이드 창, 가림·게임 UI 변경, Windows DPI 조합·설치본은 별도 검증 대상입니다.

기존 Penpot 파일에 [12명 참가 화면](https://design.penpot.app/#/view?file-id=d8ac01df-6646-81d2-8008-a69f349be8fc&page-id=d8ac01df-6646-81d2-8008-a69f349be8fd&section=interactions&frame-id=4ea68358-4b74-800d-8008-b2ad70602a7b)과 [9명 참가 화면](https://design.penpot.app/#/view?file-id=d8ac01df-6646-81d2-8008-a69f349be8fc&page-id=d8ac01df-6646-81d2-8008-a69f349be8fd&section=interactions&frame-id=4ea68358-4b74-800d-8008-b2aee718e423)을 추가했습니다. 실제 플레이어 정보를 사용하지 않은 편집 가능한 합성 화면입니다.

기존 개발자 작업 공간의 색상·글꼴을 유지하고 공대원창 크롭 탭, 검출 원본과 닉네임 경계, 2열×6행의 크롭 선택, Print Screen 안내, 로그인 중 전체 원본 전송 안내를 보여줍니다. 9명 화면은 같은 12행 창에서 아래 세 행이 비활성인 상태입니다. 실제 사용법과 수집·정답 입력 흐름은 [Desktop 안내](../../apps/desktop/README.md#공대원창-크롭)를 따릅니다.
