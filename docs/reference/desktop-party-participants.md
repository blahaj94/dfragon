# 파티참가인원 팝업 검출과 닉네임 크롭

[`@dfragon/lib`](../../packages/lib/README.md#파티참가인원-닉네임-검출크롭)의 공통 함수로 이동 가능한 파티참가인원 팝업을 찾아 각 행의 원본 닉네임 영역을 복사한다. 화면 위쪽의 가로 파티 HUD를 다루는 [기존 파티 영역 조사](desktop-party-geometry.md)와 구분한다. 이 문서는 제공된 화면에서 확인한 관측값과 현재 구현을 기록한다.

## 도메인과 범위

개발자는 캡처한 게임 client 이미지를 전달하고, 함수는 팝업 하나의 위치·배율과 네 행의 참가 여부를 반환한다. 참가자가 있는 행의 닉네임만 잘라 개발자 작업 공간의 **파티원창 크롭** 탭에서 미리보고 수집한다. 일반 사용자 화면이나 OCR 자동 실행은 추가하지 않는다.

- 네 행은 고정 슬롯이다. 중간 참가자가 나가도 아래 행이 올라가지 않는다.
- 자물쇠만 있는 행은 빈 행이다. 닉네임 열의 밝은 픽셀만으로 참가 여부를 판단하지 않는다.
- 팝업은 화면 안에서 이동하며, 해상도와 UI 크기에 따라 래스터 크기가 변한다.
- 사용자가 확인한 게임 규칙은 최소 해상도에서 UI 크기가 0%로 고정된다는 것이다. 기준 이미지는 해당 설정에서 얻었다.
- 빨간 아이콘은 위치 후보를 찾는 단서다. 네 열 헤더와 네 행 구조도 함께 맞아야 검출한다.

## 관측 좌표

UI 0% 기준 헤더는 `368 × 17`픽셀이다. 팝업 좌상단으로부터 `(14, 67)` 위치에 있으며 네 열의 배경·구분선·문자를 모두 포함한다. 호출자는 이 영역을 원본 그대로 제공한다. 아래 좌표는 이 헤더의 좌상단을 원점으로 한다.

| 대상 | UI 0% 기준 좌표 |
| --- | --- |
| 팝업 외곽 | 왼쪽 −14, 위 −67, 오른쪽 380, 아래 143: 약 `394 × 210` |
| 빨간 아이콘 중심 | `(360, −15)` |
| 행 시작 | `y = 17 + 22 × (slot − 1)` |
| 닉네임 | `x = 154..238`, `y = 행 시작 + 3..18`: `84 × 15` |
| 초상화 근거 | `x = 31..48`, `y = 행 시작 + 2..18` |
| 레벨 근거 | `x = 51..72`, `y = 행 시작 + 2..18` |
| 역할 아이콘 근거 | `x = 242..254`, `y = 행 시작 + 2..18` |

오른쪽·아래쪽은 포함하지 않는다. 배율을 적용한 각 모서리를 가장 가까운 정수로 반올림하고 반 픽셀인 경우 짝수 쪽을 택한다. 배율 계산의 부동소수점 오차를 고려해 `4 × Number.EPSILON × max(1, |좌표|)` 이내는 반 픽셀로 처리한다. 행 간격을 먼저 반올림해 누적하지 않는다. FHD UI 100%에서는 약 1.8배, 닉네임 크롭은 `151 × 27`픽셀이 관측됐다. FHD UI 0%와 최소 해상도 UI 0%에서는 같은 기준 크기가 관측됐다. 함수는 UI 설정이나 `estimateDNFUIScale` 값을 입력받지 않고 실제 헤더로 위치와 배율을 추정한다.

## 현재 탐지 순서

구현은 [`dnf-party-participants.ts`](../../packages/lib/src/dnf-party-participants.ts)와 내부 픽셀 매칭 모듈에 있다. 이미지 디코딩과 플랫폼 API는 사용하지 않는다.

1. 입력 크기·RGBA 길이·기준 헤더의 대비를 검사한다. 게임 client 입력 범위는 폭 1067~1920, 높이 600~1080 정수 픽셀이다.
2. 전체 화면에서 `R ≥ 130`, `R−G ≥ 75`, `R−B ≥ 55`인 픽셀의 8방향 연결 영역을 찾는다. 폭·높이 6~30px, 종횡비 0.65~1.5, 채움 비율 0.45 이상을 아이콘 후보로 사용한다. 후보가 128개를 넘으면 `search-limit`으로 종료한다.
3. 회색조 40 미만 픽셀의 행별 누적 개수를 한 번 계산한다. 각 후보 위치·배율에서 팝업 전체 경계와 네 행 구분선의 필요조건을 먼저 검사하고, 불가능한 위치에는 헤더 상관 연산을 쓰지 않는다. 밝은 게임 배경의 무관한 빨간 장식 때문에 정상 팝업까지 비교량 한도에 걸리던 문제를 이 순서로 수정했다. 아이콘 면적으로 초기 배율을 추정하고 주변 배율 및 1·1.8에서 헤더를 탐색한다. 헤더는 bilinear 보간하고 평균을 뺀 정규화 상관으로 비교한다. [정규화 상관의 정의](https://docs.opencv.org/4.13.0/df/dfb/group__imgproc__object.html)의 `TM_CCOEFF_NORMED`와 같은 형태의 점수이며 OpenCV runtime 의존성은 없다. 성긴 표본으로 위치·배율을 좁히고, 0.0025 간격의 배율과 근처 위치에서 전체 헤더 픽셀을 비교해 최종 0.68 이상을 요구한다. 모든 후보·배율의 성긴 비교와 전체 픽셀 비교를 합쳐 프레임당 64,000,000개 표본으로 제한하며, 다음 비교가 한도를 넘으면 `search-limit`으로 종료한다. 앞서 유효한 팝업을 찾았어도 부분 성공을 반환하지 않는다. 이 한도는 연산량 제한이며 실행 시간 보장은 아니다.
4. 팝업 전체가 client 안에 있는지 확인한다. 네 행 시작의 ±약 2 기준 픽셀 범위에서 가로 `x=4..364`의 회색조 40 미만 비율이 0.85 이상인 선이 각각 있어야 한다. 같은 위치의 후보를 합친 뒤 하나면 `found`, 없으면 `not-found`, 둘 이상이면 `ambiguous`다.
5. 각 행에서 초상화·레벨은 RGB 최댓값 100 이상 픽셀 비율이 각각 0.12·0.035 이상인지 본다. 역할 아이콘은 RGB 최댓값 120 이상이면서 최댓값−최솟값 60 이상인 비율이 0.1 이상인지 본다. 세 근거 중 둘 이상이면 참가자가 있다고 판정한다.
6. 크롭 함수는 같은 입력 프레임에서 참가 행의 닉네임 RGBA만 복사한다. 슬롯 순서를 보존하고 빈 행의 `crop`은 `null`이다. 입력 픽셀과 alpha를 바꾸지 않는다.

## 검증 결과

로컬 검증에 제공된 스크린샷 9개를 사용했다. 1920×1080 UI 0%·100%와 서로 다른 창 위치, 1067×600 UI 0%, 3번 슬롯만 참가자가 있고 1·2·4번에 자물쇠가 있는 경우를 포함한다. 이 중 한 장에서 기준 헤더를 추출했으므로 9개 전체가 독립 검증 표본은 아니다.

- TypeScript 공개 크롭 함수에서 9개 모두 창을 찾았고, 참가 행 33개를 반환했다. 모든 크롭 좌표가 먼저 수행한 이미지 실험의 좌표와 일치했다.
- 3번 슬롯만 남은 이미지에서 해당 슬롯 번호를 유지하고 나머지 세 행을 빈 행으로 반환했다.
- 검출된 팝업 영역을 어둡게 지운 합성 대조 이미지 9개에서는 모두 `not-found`였다. 실제 게임에서 창을 닫아 수집한 독립 음성 표본을 대신하지 않는다.
- 저장소의 [합성 픽셀 테스트](../../packages/lib/test/dnf-party-participants.test.mjs)는 이동·1.8배·빈 행·자물쇠·근거 부족·여러 후보·잘린 창·후보 한도·128개 큰 후보의 비교량 제한·한도 초과 시 부분 성공 거절·입력 검증·원본 RGBA 보존을 확인한다. 실제 스크린샷과 플레이어 데이터는 저장소와 CI에 포함하지 않는다.

반복 검증할 때는 호출자가 로컬 기준 헤더와 원본 화면을 RGBA로 디코딩해 두 공개 함수에 전달하고, 기대 슬롯 번호·크롭 경계·원본 픽셀 보존을 비교한다. CI의 합성 테스트 통과는 원본 화면 재검증을 뜻하지 않는다.

## 남은 검증

관측한 화면에서의 성공이며 일반적인 검출 정확도나 OCR 정확도를 보증하지 않는다. 중간 UI 단계의 실제 화면, 다른 화면 비율·DPI, 최대 길이·특수문자 닉네임, 창 가림·마우스 강조·게임 UI 변경, 실제 창 없는 화면의 오탐률은 확인하지 않았다. Windows 실시간 GDI 캡처·Print Screen·DPI·설치본과 실제 반복 성능은 별도 검증 대상이다.

## Desktop 연결

[승인 Penpot 화면](https://design.penpot.app/#/view?file-id=d8ac01df-6646-81d2-8008-a69f349be8fc&page-id=d8ac01df-6646-81d2-8008-a69f349be8fd&section=interactions&frame-id=14aaaf11-fc9c-8040-8008-b093b431c09a)을 바탕으로 기존 수집 session에 `hud`/`participants` 모드를 추가했다. 하나의 키보드 훅을 공유하며 탭 전환·해제 때 generation과 저장 commit 검사를 통해 이전 요청을 무효화한다. 미리보기 응답도 hook 수명이 끝나면 폐기한다. 참가자가 없는 행은 저장 입력에 포함하지 않고 원래 슬롯 번호를 유지한다.

`participant-window.ts`는 공통 크롭 함수 결과에서 팝업 전체의 미리보기 픽셀과 팝업 기준 닉네임 사각형을 구성한다. 검출과 크롭은 같은 RGBA 프레임을 사용한다. 기존 Win32 캡처 경로의 client 일관성·화면 경계·캡처 전후 외부 창 가림 검사를 팝업 전체에 적용한다. 탐지는 현재 main process에서 동기로 수행하며, 1초 미리보기 polling은 이전 응답이 끝나기 전 중복 요청하지 않는다. 저장은 미리보기 캐시를 사용하지 않고 새 캡처를 읽는다.

`participant-heading.json`은 사용자 제공 최소 UI 이미지의 368×17px 정적 열 헤더를 RGBA → zlib/Deflate → Base64 순서로 무손실 보관한다. 이름·파티 제목·초상화는 들어 있지 않다. 게임 자산의 권리는 [Desktop 고지](../../packages/licenses/notices/desktop/NOTICE.md)를 따른다. 공통 라이브러리에 게임 자산을 추가하지 않는다. Desktop은 `@dfragon/lib`를 빌드 의존성으로 선언하고 TypeScript/Vite/Vitest에서 해당 workspace source를 해석해 Electron main에 번들한다. 별도 dist 생성이나 설치본의 workspace 경로에 의존하지 않는다.

연결 테스트는 배포 헤더를 사용한 합성 팝업에서 3번만 남은 경우와 창/닉네임 원본 픽셀 보존을 확인한다. 수집 session·IPC·작업 공간 테스트는 모드 선택, 이전 요청 무효화, 빈 행의 선택 복원, 일부 저장 실패를 확인한다. `ui:fixture`의 developer 모드에서 기본 네 행과 `participants-sparse` 시나리오를 제공하며 게임 캡처 없이 합성 픽셀로 실제 renderer를 실행한다.

Desktop adapter에 제공 화면 9장을 다시 전달해 33개 크롭의 슬롯·경계·원본 바이트 일치를 확인했다. macOS 로컬 Node 실행에서 프레임당 약 29~101ms였으며 Windows GDI·키보드 훅·렌더러 전달 시간이나 일반적인 성능 보장은 포함하지 않는다. 밝은 배경의 무관한 빨간 장식 100개에 대한 회귀 테스트를 추가했고, 어두운 배경에서 실제 비교량 한도를 넘는 경우의 `search-limit`과 부분 성공 거절은 기존 테스트로 유지한다.

Playwright로 macOS Electron의 실제 앱 renderer를 열어 합성 파티원창을 확인했다. 900px 다크·라이트와 500px 3번만 참가한 화면에서 원본 미리보기, 주황색 경계, 빈 행 비활성화, 탭의 키보드 이동·선택 유지, 가로 넘침 없음과 renderer 오류 없음을 확인했다. 실제 게임 캡처는 이 UI fixture에서 사용하지 않는다.
