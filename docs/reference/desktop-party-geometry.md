# Desktop 파티 geometry 조사

Windows에서 측정한 게임 client 크기와 파티 frame 간격을 바탕으로 공용 geometry 계산을 준비했다. [`@dfragon/lib` 안내](../../packages/lib/README.md)는 UI 배율 후보 추정, 관측한 frame 간격을 이용한 배율 추정, 기준 crop을 슬롯 후보 좌표로 투영하는 순수 함수를 설명한다. 개발자 수집은 실제 client 영역과 각 프레임에서 검출한 HP·MP 기준점을 사용한다. 고정 간격으로 크롭 좌표를 반복하지 않으며, 아래 표본을 바탕으로 가득 찬 HP·MP와 테두리를 함께 검사한다. 사용 흐름은 [Desktop 안내](../../apps/desktop/README.md#개발자-모드)를 따른다.

## 관측과 추정

창 크기는 사용자 대화형 세션에서 실행 중인 DNF 프로세스 소유의 표시 중이고 최소화되지 않은 창을 찾아 읽었다. 게임 영역의 크기는 [`GetClientRect`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclientrect), 화면상의 원점은 [`ClientToScreen`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-clienttoscreen)으로 조회했다. 조회 동안 thread를 Per-Monitor V2 DPI aware로 두고 종료 시 복원했으며 관측 DPI는 96이었다. 일반 SSH 세션의 창 접근과 사용자 대화형 세션을 같다고 가정하지 않는다.

초기 조사에서 설정 파일 접근은 가능했지만 저장 시점에 의존하지 않도록 실제 창 조회를 선택했다. 아래 좌표 측정에는 설정 파일이나 레지스트리 값을 사용하지 않았고 프로세스 메모리는 읽지 않았다. 해상도와 UI 설정 변경은 사용자가 수행했다.

아래 배율은 관측 결과에 맞춘 후보식이다. `H`는 client 높이(px), `u`는 UI 설정값을 0~1로 바꾼 값이다.

`s = H / (H × (1 − u) + 600 × u)`

| Client 크기 | UI 설정 | 후보 배율 |
| --- | ---: | ---: |
| 1513×851 | 0% | 1 |
| 1920×1080 | 0% | 1 |
| 1920×1080 | 50% | 1.285714 |
| 1920×1080 | 100% | 1.8 |
| 1600×900 | 50% | 1.2 |
| 1067×600 | 50% | 1 |

1513×851과 1920×1080의 UI 0% 관측, 그리고 1067×600의 UI 50% 관측에서 HP·MP track은 같은 픽셀 영역에 나타났다. UI 설정이 다른 조건에서는 track 위치와 간격이 후보 배율에 가까웠다. 확대 과정의 보간과 정수 픽셀 경계 때문에 색이 채워진 부분의 폭은 배율과 정확히 비례하지 않았다. 이 식은 표본으로 추정한 값이며 게임 내부 공식이나 미측정 조건에 대한 보장은 아니다.

두 명이 보이는 초기 관측에서는 1067×600 UI 50%의 인접 track 시작점 간격이 141px, 1920×1080 UI 50%에서는 181px이었다. 각 사람의 HP·MP track 폭·높이와 세로 위치는 같았지만 바깥 장식과 아이콘은 달랐다. 따라서 공통 track 구조가 장식 요소보다 geometry 기준으로 적합하다. 이 초기 조사에서는 세 번째·네 번째 frame을 확인하지 못했다.

다음은 두 명 표본의 체력·마나가 가득 찬 바에서 관측한 단색 영역이다. 좌표는 게임 영역 상대값이며 양 끝 픽셀을 포함한다. 닉네임 크롭 경계나 바 전체 테두리의 크기로 사용하지 않는다.

| 조건 | 슬롯 | 가로 범위 | HP 세로 범위 | MP 세로 범위 |
| --- | --- | --- | --- | --- |
| 1067×600 · UI 50% | 1 | 42~140 | 27~29 | 33~35 |
| 1067×600 · UI 50% | 2 | 183~281 | 27~29 | 33~35 |
| 1920×1080 · UI 50% | 1 | 55~180 | 35~37 | 43~45 |
| 1920×1080 · UI 50% | 2 | 236~361 | 35~37 | 43~45 |

같은 조건의 두 슬롯에서 위 단색 영역은 각각 동일했다. 앞선 FHD UI 50%의 본인 단독 표본에서는 균일 구간 끝이 179px으로 관측되어 반복 캡처 사이 보간 가장자리에 1px 차이가 있었다. 내부 정수화·필터 동작까지 확정한 결과는 아니다. 실제 닉네임·화면 원문 대신 이 숫자 관측값을 문서와 테스트에 남긴다.

개발자 수집 구현 중 기존 1920×1080 게임 스크린샷에서 네 프레임을 추가 확인했다. HP·MP 색 띠는 각각 y35~37·43~45에 있었지만 가로 시작점은 아래처럼 달랐다. 이 스크린샷들의 게임 UI 설정 퍼센트는 별도로 확인하지 않았으며, 세로 구조는 초기 FHD UI 50% 관측과 같다.

| 표본 | 네 track의 가로 시작점 | 인접 간격 |
| --- | --- | --- |
| A | 54, 235, 417, 598 | 181, 182, 181 |
| B | 44, 215, 396, 577 | 171, 181, 181 |
| C | 44, 225, 406, 588 | 181, 181, 182 |

시각 확인에서도 프레임 장식이 다른 표본에서 닉네임과 프레임의 실제 가로 위치가 함께 달랐다. 단순한 잔량 색 띠 길이 차이로 처리해서는 안 된다. 특히 B는 정상 네 프레임인데 첫 간격이 다르므로, 고정 간격만 반복한 네 좌표를 실제 위치로 단정할 수 없다. 보이는 프레임의 관측 앵커를 우선 사용하고 공용 투영 좌표는 후보로 구분한다. 원본 스크린샷과 실제 닉네임은 저장소에 포함하지 않는다.

## 장식과 무관한 템플릿 후보

프레임 장식은 파티원 각자의 설정에 따라 달라진다. 다른 사람의 좌표를 일정 간격으로 외삽하거나 장식별 고정 이동량을 추측하지 않고, 각 HP·MP track을 독립 검출하는 방향으로 조사한다.

위 세 표본의 12개 track에서 색 띠 시작점을 `a`라고 할 때, `x=a−1..a+127`, `y=34..46`의 129×13px 영역을 비교했다. 휘도 40 미만의 어두운 픽셀로 구분하면 y34·39·41·46의 수평선이 각각 12개 중 10개 이상에서 같은 가로 구간에 남았다. RGB 값이 완전히 같다는 결과는 아니다. 바깥 장식 영역인 `x=a−8..a−2`, `a+128..a+140`에는 같은 공통성이 없어 템플릿에서 제외하는 후보로 잡았다.

이는 잔량 내부 픽셀을 마스킹한 HP·MP 경계 템플릿을 시험할 근거다. 세 표본은 모두 거의 가득 찬 상태이므로 잔량이 줄거나 빈 상태에서 경계가 유지되는지는 확인하지 못했다. 어두운 수평선만으로는 배경을 잘못 검출할 수 있어 두 track의 상대 위치, 밝고 어두운 경계 대비, 크기별 일치도도 검증해야 한다. 제품 검출기는 RGB 원문을 그대로 비교하지 않고 HP·MP 색 분류, 세로 중심과 간격, 가로 폭, 주변 경계의 어두운 픽셀 비율을 함께 비교한다. 이 표본 밖의 모든 장식에 대한 정확도를 보장하는 결과는 아니다.

이번 구현 범위는 파티 결성 중 HP·MP가 가득 찬 화면이다. 잔량이 줄어든 전투 화면의 검출은 요구하지 않으므로, 가득 찬 HP·MP 색 띠와 테두리를 함께 확인하는 템플릿을 사용한다. 조건에 맞지 않는 프레임은 추측해서 저장하지 않는다. 템플릿으로 찾은 기준점과 실제 닉네임 영역을 함께 확인한 뒤 저장 경계를 정한다. 학습용 저장 이미지는 닉네임만 포함하고, HP·MP 영역은 위치 검출과 가림 확인에만 사용한다.

세 표본의 네 프레임을 실제 검출 코드로 확인했다. 배율은 보간과 색 경계에 따라 1.28~1.30으로 관측되며 게임 UI 설정값 자체를 뜻하지 않는다. 파티 번호는 누락된 프레임을 앞으로 당겨 번호를 붙이지 않도록 서로 겹치지 않는 넓은 위치 범위로 식별한다. 이 범위는 번호 식별용이며 실제 크롭의 가로 위치는 검출한 HP·MP 시작점으로만 정한다.

Windows 10의 실제 1067×600 화면에서도 한 프레임 검출과 원본 크롭을 확인했다. 기존 왼쪽 시작점은 첫 글자 외곽선을 일부 잘라내어, 관측한 바의 시작점부터 여백을 포함하도록 수정했다. 현재 이름 영역은 `x=관측 시작점`, `y=floor(12s)`, `width=ceil(72.5s)`, `height=ceil(12s)`다. 기본 표본의 글자·외곽선과 위 FHD 12개 이름이 경계 안에 들어오는 것을 확인했으며, 최대 길이 이름은 아직 검증하지 않았다.

## 공용 함수의 범위

`estimateDNFUIScale`은 UI 설정값과 client 높이로 배율 후보를 계산하고, `estimateDNFPartyScale`은 관측한 인접 track 간격으로 배율을 추정한다. `projectDNFPartyRegions`는 호출자가 보정한 기준 crop과 배율을 네 위치로 투영한다. 기준 slot 간격은 141px 관측에 근거하며 세 번째·네 번째 위치는 첫 두 위치의 간격을 외삽한다. 자세한 입력 범위와 정수 좌표 처리는 [패키지 안내](../../packages/lib/README.md)를 따른다.

이 함수들은 frame이나 닉네임 위치를 자동 검출하거나, 파티원의 존재를 판정하거나, 화면을 캡처하지 않는다. 투영할 기준 crop은 호출자가 보정해야 하며 범위를 벗어나는 영역은 오류로 처리한다.

Desktop 수집은 client 기준점을 사용하며 OCR 전처리와 원본 저장 처리를 분리한다. 1초 간격 미리보기는 저장하지 않고, Print Screen을 눌렀을 때 새 프레임에서 선택한 최대 네 개의 원본 crop을 저장한다. 게임 뒤 정답 입력 탭에서 이미지를 하나씩 라벨하거나 제외·복원한다. 주기적인 파일 저장과 일괄 라벨링은 하지 않는다.

화면에서 구한 raster 배율과 게임 설정의 UI 퍼센트는 구분한다. 특히 client 높이가 600px이면 위 식은 모든 UI 설정에서 배율 1이므로 UI 퍼센트를 역산할 수 없다. 개발자 화면은 관측한 배율을 표시하며 UI 설정값을 읽었다고 주장하지 않는다.

## Print Screen 실제 검증

Windows 10의 1067×600·한 프레임 화면에서 실제 키보드의 Print Screen으로 새 원본 PNG 한 장이 저장되는 것을 확인했다. 저장 전 샘플은 없었고 저장 후 1번 위치의 미작성 정답(`null`) 샘플 한 장이 있었으며, 수집 종료 후 등록 해제도 성공했다. 미리보기 시점보다 새로 캡처한 데이터를 저장했다.

검증 중 Electron 전역 단축키 등록이 거절되어 `WH_KEYBOARD_LL` 대체 등록을 사용했다. 던파는 관리자 권한, 검증 앱은 일반 권한일 때 등록이 성공해도 키 이벤트가 전달되지 않았다. 두 프로세스를 관리자 권한으로 맞추자 실제 키의 눌림·해제 이벤트와 저장을 확인했다. 제품은 활성화 전에 이 권한 차이를 검사해 재실행을 안내하고 자동으로 권한을 올리지 않는다. 추가한 권한 검사도 실제 Windows에서 일반 권한은 `DEVELOPER_ADMIN_REQUIRED`, 관리자 권한은 통과하는 것을 확인했다. 훅은 수집 중에만 유지하며, 게임 전경의 Print Screen 외 입력은 그대로 전달한다.

macOS에서는 Playwright로 실제 Electron UI의 수집·정답 입력 탭, 체크박스 유지, 정답 저장·제외·복원, 탭 전환 시 미저장 입력 유지와 900px·500px 화면을 확인했다. 이는 Windows 설치 패키지 전체 실행이나 DPI 조합 검증을 대체하지 않는다.

## 남은 확인

- 직접 설정을 바꾼 대화형 측정은 self frame과 두 명이 보이는 상태까지다. 추가 FHD 스크린샷에서는 세 번째·네 번째 위치와 장식에 따른 가로 차이를 확인했지만, 모든 해상도·UI 배율에서 검증한 것은 아니다. Occupancy 판단은 별도 문제다.
- HP·MP 잔량이 줄거나 비어 있는 프레임의 검출은 이번 지원 범위 밖이다. 가득 찬 바와 테두리 조건을 함께 검사하고, 불일치 시 미검출로 처리해야 한다.
- 긴 닉네임의 crop 경계, 다양한 HP·MP 잔량, UI 효과·가림, client 크기 변경, 창 배치와 DPI가 달라질 때의 동작은 검증하지 않았다.
- 다음 보정에서는 긴 닉네임을 포함하고 최소·최대 client 크기에서 track 및 crop 경계를 비교한다. 3~4명 화면의 다양한 배율에서도 관측 앵커를 비교한다. 자동 frame 검출의 정확도는 산식 테스트와 별도로 확인해야 한다.
