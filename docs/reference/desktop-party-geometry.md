# Desktop 파티 geometry 조사

Windows에서 측정한 게임 client 크기와 파티 frame 간격을 정리한다. 일반 캡처는 실제 client 영역과 각 프레임에서 검출한 HP, MP 기준점을 사용한다. 고정 간격으로 크롭 좌표를 반복하지 않으며, 아래 표본을 바탕으로 가득 찬 HP, MP와 테두리를 함께 검사한다. 사용 흐름은 [Desktop 안내](../../apps/desktop/README.md)를 따른다.

## 관측과 추정

게임 영역 크기는 실행 중인 DNF 창의 [`GetClientRect`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclientrect)로 읽었다. 설정 파일, 레지스트리, 프로세스 메모리는 사용하지 않았다.

아래 배율은 관측 결과에 맞춘 후보식이다. `H`는 client 높이(px), `u`는 UI 설정값을 0~1로 바꾼 값이다.

`s = H / (H × (1 − u) + 600 × u)`

| Client 크기 | UI 설정 | 후보 배율 |
| --- | ---: | ---: |
| 1513×851 | 0% | 1 |
| 1920×1080 | 0% | 1 |
| 1920×1080 | 50% | 1.285714 |
| 1920×1080 | 100% | 1.8 |
| 1600×900 | 50% | 1.2 |
| 1067×600 | 50% | 1 |

1513×851과 1920×1080의 UI 0% 관측, 그리고 1067×600의 UI 50% 관측에서 HP, MP track은 같은 픽셀 영역에 나타났다. UI 설정이 다른 조건에서는 track 위치와 간격이 후보 배율에 가까웠다. 확대 과정의 보간과 정수 픽셀 경계 때문에 색이 채워진 부분의 폭은 배율과 정확히 비례하지 않았다. 이 식은 표본으로 추정한 값이며 게임 내부 공식이나 미측정 조건에 대한 보장은 아니다.

인접 HP, MP track 시작점 간격은 1067×600 UI 50%에서 141px, 1920×1080 UI 50%에서 181px이었다. 사람마다 track 폭, 높이와 세로 위치는 같았지만 바깥 장식과 아이콘은 달랐으므로 공통 track 구조를 geometry 기준으로 쓴다. 1920×1080 스크린샷 세 장의 네 track 가로 시작점 간격은 171~182px로, 프레임 장식에 따라 닉네임과 프레임의 가로 위치가 함께 달랐다. 따라서 고정 간격만 반복한 네 좌표를 실제 위치로 단정하지 않고, 보이는 프레임의 관측 앵커를 사용한다. 원본 스크린샷과 실제 닉네임은 저장소에 포함하지 않는다.

## 장식과 무관한 템플릿 후보

프레임 장식은 파티원 각자의 설정에 따라 달라진다. 다른 사람의 좌표를 일정 간격으로 외삽하거나 장식별 고정 이동량을 추측하지 않고, 각 HP, MP track을 독립 검출하는 방향으로 조사한다.

1920×1080 세 표본의 12개 track에서 색 띠 시작점을 `a`라고 할 때, `x=a−1..a+127`, `y=34..46`의 129×13px 영역을 비교했다. 휘도 40 미만의 어두운 픽셀로 구분하면 y34, 39, 41, 46의 수평선이 각각 12개 중 10개 이상에서 같은 가로 구간에 남았다. RGB 값이 완전히 같다는 결과는 아니다. 바깥 장식 영역인 `x=a−8..a−2`, `a+128..a+140`에는 같은 공통성이 없어 템플릿에서 제외하는 후보로 잡았다.

이는 잔량 내부 픽셀을 마스킹한 HP, MP 경계 템플릿을 시험할 근거다. 세 표본은 모두 거의 가득 찬 상태이므로 잔량이 줄거나 빈 상태에서 경계가 유지되는지는 확인하지 못했다. 어두운 수평선만으로는 배경을 잘못 검출할 수 있어 두 track의 상대 위치, 밝고 어두운 경계 대비, 크기별 일치도도 검증해야 한다. 제품 검출기는 RGB 원문을 그대로 비교하지 않고 HP, MP 색 분류, 세로 중심과 간격, 가로 폭, 주변 경계의 어두운 픽셀 비율을 함께 비교한다. 이 표본 밖의 모든 장식에 대한 정확도를 보장하는 결과는 아니다.

이번 구현 범위는 파티 결성 중 HP, MP가 가득 찬 화면이다. 잔량이 줄어든 전투 화면의 검출은 요구하지 않으므로, 가득 찬 HP, MP 색 띠와 테두리를 함께 확인하는 템플릿을 사용한다. 조건에 맞지 않는 프레임은 추측해서 저장하지 않는다. 템플릿으로 찾은 기준점과 실제 닉네임 영역을 함께 확인한 뒤 저장 경계를 정한다. 학습용 저장 이미지는 닉네임만 포함하고, HP, MP 영역은 위치 검출과 가림 확인에만 사용한다.

세 표본의 네 프레임을 실제 검출 코드로 확인했다. 배율은 보간과 색 경계에 따라 1.28~1.30으로 관측되며 게임 UI 설정값 자체를 뜻하지 않는다. 파티 번호는 누락된 프레임을 앞으로 당겨 번호를 붙이지 않도록 서로 겹치지 않는 넓은 위치 범위로 식별한다. 이 범위는 번호 식별용이며 실제 크롭의 가로 위치는 검출한 HP, MP 시작점으로만 정한다.

현재 [`HUD geometry 검출기`](../../packages/lib/src/dnf-party-frame-geometry.ts)는 색상
채널의 `trackColorPolicy`, 색 띠 병합의 `bandPolicy`, 중심, 폭 오차와 점수 가중치의 `pairPolicy`,
가득 찬 폭의 `fullTrackPolicy`, 주변 테두리의 `edgePolicy`, 중복, 배율 묶기의 `candidatePolicy`를
구분한다. 같은 숫자여도 다른 보정 의미는 공유하지 않으며 실측 임계값과 비교 연산자는 유지한다.
HP, MP 기준 중심 간격은 `34 − 28`에서 파생한 6px로 배율을 적용한다. 이름 크롭의 기준 위, 폭, 높이는
`nameReferenceRegion`의 12, 72.5, 12px이며 아래의 고정 세로 여백과 `floor`/`ceil` 계산을 유지한다.
정책 명명은 검출 민감도 조정이나 새로운 게임 화면, DPI의 재검증을 뜻하지 않는다.

Windows 10의 실제 1067×600 화면에서도 한 프레임 검출과 원본 크롭을 확인했다. 기존 왼쪽 시작점은 첫 글자 외곽선을 일부 잘라내어, 관측한 바의 시작점부터 여백을 포함하도록 수정했다. 기존 이름 영역 `x=관측 시작점`, `y=floor(12s)`, `width=ceil(72.5s)`, `height=ceil(12s)`에서 기본 표본의 글자, 외곽선과 위 FHD 12개 이름이 경계 안에 들어오는 것을 확인했다. 이후 사용 중 세로 여백이 좁다는 피드백에 따라 위아래 각각 원본 화면 기준 2px을 추가했다. 현재 영역은 `x=관측 시작점`, `y=floor(12s)−2`, `width=ceil(72.5s)`, `height=ceil(12s)+4`다. 추가 여백은 UI 배율과 무관하게 고정 2px이며 미리보기와 새 저장 이미지에 동일하게 적용한다. 기존 저장 이미지는 변경하지 않는다. 최대 길이 이름은 아직 검증하지 않았다.

## 일반 캡처의 검출

`detectPartyFrameGeometry`를 `@dfragon/lib`에서 제공하며 일반 OCR 캡처가 사용한다. 1920×1080 일치 조건과 1067×600~1920×1080 client 필터를 제거했다. `isValidPartyFrameSize`는 양의 정수 크기, 한 변 8192px 이하, 총 33,000,000픽셀 이하를 확인한다.

일반 캡처는 Alt+R로 읽은 회차 프레임 한 장에서 HP, MP를 검출한 위치만 원본 크기로 자른 뒤 Otsu 반전 이진화 OCR을 적용한다. 미검출 슬롯은 해당 회차에서 비워 두며 누락된 슬롯의 번호를 당기지 않는다. 해상도가 바뀌거나 가림이 사라진 화면은 다음 Alt+R 회차에서 새로 검출한다. 영상은 게임 client 원점과 일치해야 하므로 일반 캡처의 테두리 없는 창 조건은 유지한다.

해상도 확대 사례는 합성 픽셀로 검증하며, 아래 실측 이력과 구분한다. macOS Electron의 실제 3840×2160 합성 창 캡처에서 네 닉네임 OCR, 중지 후 자원 해제, 재선택을 확인했다. 테스트 Canvas는 Retina 배율의 물리 픽셀에 그리며 영상 크기를 FHD로 축소하지 않는다. QHD, 4K의 실제 게임, Windows DPI, 모든 장식과 배율 조합을 검증했다는 뜻은 아니다.

## 배율 표시

화면에서 구한 raster 배율과 게임 설정의 UI 퍼센트는 구분한다. 특히 client 높이가 600px이면 위 식은 모든 UI 설정에서 배율 1이므로 UI 퍼센트를 역산할 수 없다. 화면에 배율을 보일 때도 UI 설정값을 읽었다고 주장하지 않는다.

## 남은 확인

- 직접 설정을 바꾼 대화형 측정은 self frame과 두 명이 보이는 상태까지다. 추가 FHD 스크린샷에서는 세 번째, 네 번째 위치와 장식에 따른 가로 차이를 확인했지만, 모든 해상도, UI 배율에서 검증한 것은 아니다. Occupancy 판단은 별도 문제다.
- HP, MP 잔량이 줄거나 비어 있는 프레임의 검출은 이번 지원 범위 밖이다. 가득 찬 바와 테두리 조건을 함께 검사하고, 불일치 시 미검출로 처리해야 한다.
- 긴 닉네임의 crop 경계, 다양한 HP, MP 잔량, UI 효과, 가림, client 크기 변경, 창 배치와 DPI가 달라질 때의 동작은 검증하지 않았다.
- 다음 보정에서는 긴 닉네임을 포함하고 최소, 최대 client 크기에서 track 및 crop 경계를 비교한다. 3~4명 화면의 다양한 배율에서도 관측 앵커를 비교한다. 자동 frame 검출의 정확도는 산식 테스트와 별도로 확인해야 한다.
