# 캐릭터 상세 정보

사용자가 검색 결과에서 선택한 캐릭터를 Neople에서 조회해 JSON으로 정제해 제공한다. API는 DB를 쓰지 않는다(2026-10-26 결정, [Issue #796](https://github.com/blahaj94/dfragon/issues/796)). [캐릭터 조회](#캐릭터-캐시와-강제-갱신)는 API 메모리에 1시간, [공용 아이템 상세](#공용-아이템-상세)는 24시간 캐시한다(2026-10-29 결정, [Issue #992](https://github.com/blahaj94/dfragon/issues/992)). API가 서버 한 대, 인스턴스 하나라 캐시를 Redis 대신 프로세스 메모리에 두며, 노드가 늘면 여러 노드가 공유하는 Redis로 옮긴다.

## 조회와 응답

`GET /characters/:serverId/:characterId`는 로그인 없이 제공한다. 서버는 지원하는 단일 서버 ID이며 `all`은 받지 않는다. 캐릭터 ID는 대소문자를 보존하는 1~256자의 ASCII 영숫자, `_`, `-`다. Query parameter와 HEAD는 400이다. 캐시를 건너뛰는 `POST /characters/:serverId/:characterId/refresh`는 [강제 갱신](#캐릭터-캐시와-강제-갱신)에 있다.

조회 대상은 기본정보, 능력치, 장착장비, 아바타, 크리쳐, 서약, 안개융화, 스킬스타일, 버프 강화 장비, 아바타, 크리쳐의 11개다. 타임라인, 과거 이력, 통계 집계와 Electron 상세 화면은 이 범위에 포함하지 않는다.

같은 프로세스에서 동일 서버, 캐릭터의 Neople 조회가 겹치면 하나의 조회를 공유한다. 각 HTTP 요청의 공용 상세 연결은 개별 처리한다. 대기자 하나의 연결 종료는 다른 대기자의 조회를 취소하지 않으며, 마지막 대기자가 사라지면 공유 작업도 취소한다. 서버 종료는 모든 공유 작업과 공용 아이템 묶음 호출을 취소하고 정리를 기다린다. 여러 인스턴스 사이의 실행 공유는 보장하지 않는다.

기본정보로 식별을 확인한 뒤 나머지 10개 섹션을 동시 실행 제한 없이 한 번에 병렬 조회한다([호출 제한 결정](character-search.md#공개-검색과-호출-제한)). Neople 요청 대기는 API가 따로 두는 기한 없이 HTTP client 기본 timeout을 따르고, timeout은 504 `NEOPLE_TIMEOUT`으로 반환한다. 자동 재시도하지 않는다. 요청된 캐릭터, 서버와 공통 이름, 섹션의 필수 envelope를 검사한다. 시즌별 중첩 옵션은 엄격한 고정 schema로 제한하지 않으며 미장착을 나타내는 null과 알 수 없는 추가 필드를 원본에 보존한다.

11개가 모두 성공해야 응답한다. 하나라도 실패하면 오류를 반환하며 부분 결과를 성공처럼 돌려주지 않는다. 여러 upstream 호출이 게임 서버의 같은 순간을 나타낸다고 보장하지는 않는다.

응답은 `character`, `status`, `equipment`, `avatar`, `creature`, `oath`, `mistAssimilation`, `skillStyle`, `buff`, `sections`, `freshness`, `card`다. 공통 신상 정보는 `character`로 모으고 반복되는 헤더를 제거한다. 장비별 옵션은 보존한다. `sections`에는 섹션별 revision, 내용 갱신 시각, 최근 성공 조회 시각을 제공한다. 11개 섹션을 한 번에 받아 통째로 캐시하므로 revision은 항상 1이고 두 시각은 그 값을 Neople에서 실제로 받은 시각이다. 최상위 `freshness.lastSuccessfulFetchAt`도 같은 시각이고, `freshness.expiresAt`은 그 시각에 1시간을 더한 ISO 시각으로 캐시가 끝나는 때다. 캐시한 값이면 처음 받은 시각이 그대로 나간다. 기존 Desktop과의 호환을 위해 이 필드들의 형태를 유지한다.

## 캐릭터 캐시와 강제 갱신

캐릭터 하나의 기본정보와 섹션 10개를 묶어 서버, 캐릭터 ID별로 API 메모리에 1시간 캐시한다. 1시간 안에 같은 캐릭터를 다시 조회하면 Neople을 부르지 않는다. 장비를 바꾼 직후 최대 1시간 동안 옛 장비와 점수가 보일 수 있는 것은 감수한다(2026-10-29 결정, [Issue #992](https://github.com/blahaj94/dfragon/issues/992)). 11개를 모두 받은 조회만 캐시하며, 실패한 조회는 캐시하지 않아 다음 요청이 다시 조회한다. 캐시는 캐릭터 1,000명까지 두고, 넘으면 가장 오래 쓰지 않은 캐릭터부터 버린다. 캐릭터 하나에 원본 섹션 약 35KB, [저장한 응답 본문](#응답-본문-재사용) 약 150KB가 들어 1,000명이면 약 185MB로 추정한다. 2026-10-30 운영 부하 테스트에서 캐릭터 캐시가 다 찬 뒤 API RSS는 약 300MB에서 멈췄다([#870 기록](https://github.com/blahaj94/dfragon/issues/870)). 운영자가 알려 준 컨테이너 메모리 한도 약 4GB 기준으로 응답 본문이 더해져도 여유가 있다. 캐시가 다 찬 상태의 heap 사용량은 재지 않았다.

`POST /characters/:serverId/:characterId/refresh`는 로그인 없이 제공하는 강제 갱신이다. 캐릭터 캐시를 건너뛰고 기본정보와 섹션을 Neople에서 다시 받아 캐시를 덮어쓴 뒤, 상세 GET과 같은 응답을 돌려준다. 공용 아이템 상세는 강제 갱신에서도 캐시를 그대로 쓴다. 같은 캐릭터를 이미 Neople에서 받는 중이면 새로 부르지 않고 그 조회를 함께 기다린다. 강제 갱신 중에 들어온 상세 GET은 캐시에 남은 값이 있으면 그 값을 받는다.

강제 갱신이 새로 받지 못하면 상세 GET과 같은 오류 응답을 돌려주고 기존 캐시는 그대로 둔다. 경로 입력 검증, query 거절, 오류 형식은 상세 GET과 같다. Body는 읽지 않는다.

저장한 응답 본문을 보낸 요청은 Neople도 공용 아이템도 기다리지 않으므로 접근 로그에 `neopleMs` 없이 `responseCached: true`가 붙는다. 캐릭터 캐시는 맞았지만 저장한 본문이 없는 요청은 `neopleMs`에 `basic`, `sections` 없이 `catalog`만 남는다. 진행 중인 조회에 합류한 요청에는 `neopleShared: true`가 붙는다. 형식은 [접근 로그](../../apps/api/README.md#접근-로그)에 있다.

## 응답 본문 재사용

캐릭터 캐시 항목마다 완성한 응답 JSON 본문을 함께 둔다(2026-10-30 결정, [Issue #996](https://github.com/blahaj94/dfragon/issues/996)). 캐시가 맞은 상세 GET은 응답을 다시 조립하거나 직렬화하지 않고 저장한 본문을 그대로 보낸다. 저장한 본문은 캐시 없이 만든 응답과 바이트 단위로 같고 `Content-Type: application/json; charset=utf-8`도 같다. 캐릭터 항목이 만료되거나 밀려나거나 강제 갱신으로 바뀌면 본문도 함께 사라진다. 강제 갱신이 새로 만든 응답은 이후 상세 GET이 보내는 본문이 된다.

공용 아이템 상세가 하나라도 `unavailable`인 응답은 저장하지 않는다. 다음 요청이 그 아이템을 다시 조회하게 하기 위해서다. 저장한 본문 안의 공용 아이템 상세는 캐릭터 항목이 사는 동안(최대 1시간) 고정된다. 그 사이 공용 아이템 캐시가 새 값을 받아도 이 본문에 반영되지 않는 것은 감수한다(2026-10-30 결정, [Issue #996](https://github.com/blahaj94/dfragon/issues/996)).

응답 압축은 API가 하지 않고 운영 Caddy가 맡는다(2026-10-30 결정). 저장한 본문도 압축하지 않은 채 보내며, Caddy가 요청의 `Accept-Encoding`에 맞춰 zstd나 gzip으로 압축한다.

## 카드 투영

응답 최상위 `card`는 Desktop 카드의 캐릭터 면이 쓰는 역할이다. 형태는 [#716](https://github.com/blahaj94/dfragon/issues/716)의 공유 계약을 따르며 `apps/api/src/characters/card/project.ts`의 순수 함수가 HTTP 없이 만든다. Desktop은 캐릭터 면만 두므로 API는 역할만 정한다(2026-10-26 결정, [Issue #796](https://github.com/blahaj94/dfragon/issues/796)).

- `role`: 기본정보 `jobGrowName`에서 앞의 `眞`을 뺀 이름이 크루세이더, 인챈트리스, 패러메딕, 뮤즈면 `buffer`, 다른 문자열이면 `dealer`, 문자열이 아니면 null이다. Desktop은 이 값으로 점수 계산기를 고른다.
- `score`: 항상 null이다. 장비 점수는 Desktop main이 네이티브 점수 엔진으로 채운다. 서버는 점수를 계산하지 않는다.
- `stats`, `serverRank`, `set`, `oath`는 항상 null이고 `investment`는 항상 빈 배열이다. 카드의 스탯 한 줄, 서버 내 명성 순위, 장비 면, 기타 면에 쓰던 값이다. 이미 배포된 Desktop이 카드 전체를 strict 스키마로 검사하므로, 그 버전이 역할과 점수를 계속 표시하도록 필드만 남긴다. 새 Desktop은 역할만 읽는다.

모험단명으로 저장된 캐릭터를 찾던 `GET /adventures/characters`도 DB에만 있던 기능이라 지웠다. 이 경로는 일반 404다.

## 공용 아이템 상세

조회한 캐릭터 11개 섹션에 공용 상세를 연결한다. 원본 캐릭터 섹션에는 공용 상세를 섞지 않는다. 일반, 버프 장착 장비, 아바타, 엠블렘, 외형 clone, 크리쳐, 아티팩트, 외형 clone, 서약 info, 결정, 버프 아바타, 엠블렘, 외형 clone과 버프 크리쳐의 유효한 itemId가 있는 각 항목에 `itemDetail: { data, fetchedAt, status }`를 추가한다. `itemDetail`은 서버 응답용으로 예약한 필드다. ID가 없는 빈 슬롯, null, 빈 배열, 선택 옵션과 원본 배열 순서는 유지한다. 외형 clone의 상세를 장착 효과로 합산하지 않는다.

공용 상세는 아이템 ID별로 API 메모리에 24시간 캐시한다. 공용 아이템은 캐릭터와 상관없는 아이템 정의라 게임 패치 사이에는 누가 조회해도 같다. 게임 패치 직후 최대 24시간 동안 옛 아이템 설명이나 수치가 나갈 수 있는 것은 감수한다(2026-10-29 결정, [Issue #992](https://github.com/blahaj94/dfragon/issues/992)). 캐시는 아이템 1만 개까지 두고, 넘으면 가장 오래 쓰지 않은 아이템부터 버린다. 아이템 하나가 약 1KB라 약 10MB다.

`fresh`는 유효 기간 안의 값이고, `fetchedAt`은 그 값을 Neople에서 실제로 받은 시각이다. 캐시한 값이면 처음 받은 시각이 그대로 나간다. `unavailable`은 조회 실패나 응답 누락으로 data와 fetchedAt이 null인 상태다. 조회에 실패했거나 Neople 응답에 없던 아이템은 캐시하지 않아 다음 요청이 다시 조회한다. 공용 조회 실패는 성공한 캐릭터 응답을 실패로 바꾸지 않는다. 클라이언트 연결 종료와 서버 종료는 전체 요청을 취소한다.

아이템 다중 조회는 최대 15개를 ID로 대응하고, 없는 항목이나 중복 응답 항목은 unavailable로 둔다. 스킬과 세트의 공용 상세는 조회하지 않으며 아이템 상세의 setItemId로 후속 조회하지 않는다.

공용 아이템 참조는 요청마다 중복 제거 후 최대 128개를 처리한다. 초과 참조는 unavailable로 전달하며 캐릭터 원본은 유지한다. 캐시에 없는 아이템은 같은 tick에 들어온 다른 상세 요청의 아이템과 함께 모아 중복 없이 15개씩 묶어 호출하고, 묶음 호출은 동시 실행 제한 없이 모두 동시에 시작한다([호출 제한 결정](character-search.md#공개-검색과-호출-제한)). 이미 조회 중인 아이템은 새로 호출하지 않고 그 조회를 함께 기다린다.

공용 상세 조회에는 API가 따로 두는 기한이 없고, Neople 응답 대기는 HTTP client 기본 timeout을 따른다. 요청은 클라이언트가 연결을 끊으면 공용 상세 기다림을 그만둔다. 묶음 호출은 여러 요청이 공유하므로 한 요청의 연결 종료로 취소하지 않고 서버 종료 때만 취소하며, 기다림을 그만둔 요청이 시작한 호출도 끝나면 결과를 캐시에 남긴다. 자동 재시도는 없으며 여러 인스턴스 사이의 캐시와 실행 공유는 보장하지 않는다.

장비 슬롯 수, 세트 개수, 마법부여의 직업별 스킬 증가, 숫자, 문자열 능력치, 스킬 필드 누락, 체인의 null과 배열 순서를 보존한다. 공용 tune 등의 값으로 캐릭터 장착 값을 덮어쓰지 않는다. 공용 상세는 실제 적용 능력치 계산 결과나 마법부여 평가가 아니다.

## 오류, 호출 제한

상세 GET과 강제 갱신에는 클라이언트별 호출 제한과 서버 전체 Neople 호출 예산이 없다. 결정과 위험은 [공개 검색과 호출 제한](character-search.md#공개-검색과-호출-제한)에 있다. 캐릭터 캐시에 없는 상세 요청과 강제 갱신은 Neople 11회를 소비하고, 1시간 안에 다시 조회한 캐릭터는 Neople을 부르지 않는다. 공용 아이템은 24시간 안에 받은 아이템을 다시 부르지 않고, 캐시에 없는 아이템만 15개씩 묶어 호출한다. 연결 해제, 종료 신호를 확인해 취소된 요청의 후속 처리를 중단한다.

오류 body는 `error.code`, `error.message`만 가진다. 입력 400 `INVALID_CHARACTER_QUERY`, 내부 오류 500 `INTERNAL_SERVER_ERROR`, 공급자 오류 502 `NEOPLE_API_ERROR`, 이용 불가 503 `NEOPLE_UNAVAILABLE`, Neople 제한 시간 504 `NEOPLE_TIMEOUT`이다. 공급자 code 분류는 기존 검색과 같고 상세 조회용 고정 문구로 반환한다. 키, 공급자 원문 오류, 요청 원문을 로그나 응답에 포함하지 않는다.
