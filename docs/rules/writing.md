# 설명과 GitHub 글 작성 기준

## 사람이 읽는 설명 작성 기준

결론이나 달라지는 동작을 먼저 설명하고 판단에 필요한 이유·근거를 잇는다. 자연스러운 한국어로 쓰며 코드 식별자·명령·계약 값은 정확히 유지한다. 질문과 독자의 맥락에 맞춰 설명하고 이미 아는 내용이나 원문 Rule·대화를 반복하지 않는다.

확인한 사실, 추정, 제안, 미완료·미검증을 구분한다. 중요한 제약과 실패를 짧게 쓰기 위해 생략하지 않는다. 완료 조건은 구체적인 상황과 기대 결과로 설명한다.

## GitHub 글의 문체와 형식

Issue·PR·댓글은 한국어 존댓말로 필요한 사실을 전달한다. 제목은 대상과 변경을 알아볼 수 있으면 된다. 관련 기록이 필요할 때 링크로 연결하며 역할별 양식, 고정 항목, 반복된 “해당 없음”을 요구하지 않는다. 기존 글 전체를 일괄 수정하지 않는다.

한 문단에 하나의 중심 내용을 담고 정보 역할이 달라지면 빈 줄을 넣는다. 목록·표는 비교나 나열에 도움이 될 때 사용한다. 코드·정확한 원문 이외에서 문자 그대로의 `\n`이나 `<br>`로 문단을 대신하지 않는다. Commit 제목은 한 줄, 필요한 본문은 빈 줄 뒤에 둔다.

링크는 내용을 알 수 있는 이름으로 붙인다. 외부 자료는 실제로 확인한 필요한 부분만 요약·인용한다. 게시할 때 실제 개행과 Markdown 표시를 확인하고 사실·링크가 맞는지 점검한다.

Secret·token·credential·개인정보·개인 경로·내부 대화 및 실행 식별자·raw log를 공개 기록에 넣지 않는다. 예시는 명확한 placeholder를 사용한다. 과거 승인·실패·완료 증거는 보존한다.
