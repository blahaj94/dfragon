# 코드 재사용

기존 구현, 런타임의 표준 API, 적합한 설치 패키지를 먼저 사용한다. 요구에 맞는 기능이 없고 외부 후보 검토가 판단에 도움이 될 때 필요한 범위만 조사한다. 모든 helper에 외부 검색·비교 문서·사용자 선택을 요구하지 않는다. 기존 결정이 요구·환경·사용 역할에 여전히 맞으면 재조사하지 않는다.

범용 기능과 제품 정책을 구분한다. URL 파싱과 허용 URL 정책은 다른 책임이다. 사용 횟수나 코드 길이만으로 재사용·공통화·자체 구현을 결정하지 않는다. 같은 이유로 변경되는 책임은 공유할 수 있고, 비슷해도 다른 이유로 바뀌는 코드는 억지로 합치지 않는다.

## 선택과 유지보수

요청 범위 안의 통상적인 dependency와 구현 선택은 담당자가 판단하고 중요한 이유를 PR이나 기존 결정 위치에 남긴다. 명시적 금지, 중요한 라이선스·보안·배포·비용 영향과 새 architecture 방향은 [판단과 권한](agent-workflow.md#판단과-권한)을 따른다.

적합한 기존 기능이 없으면 직접 구현의 보장 범위와 유지보수 책임을 판단한다. 범용 프로토콜·암호·경합 처리처럼 책임이 큰 구현은 단순 helper로 위장하거나 승인 질문을 피하는 수단으로 만들지 않는다. 실질적인 사용자 선택이 필요하면 권장안·대안과 영향을 제시한다. 비교는 작성뿐 아니라 테스트·mock·리뷰·유지보수와 외부 패키지의 통합·업데이트 비용을 포함하되 형식적인 비용 보고서를 만들지 않는다.

Wrapper는 공통 정책이나 실제 경계를 제공할 때만 둔다. 외부 호출을 그대로 전달하거나 library의 일반 기능을 다시 구성하는 계층은 피한다. 선택한 구현의 계약·실패·지원 범위는 소유 모듈과 필요한 검증에서 찾을 수 있게 한다. 변경된 요구·환경·보장·라이선스·보안 문제에 영향을 받는 결정만 재검토한다.

## 앱 내부 모듈과 공통 패키지

같은 책임은 먼저 소유 앱의 모듈에 둔다. 별도 package는 독립 계약, 앱으로 되돌아가지 않는 의존성, 실제 경계 이점이 있을 때 검토한다. 여러 소비자의 동일 계약 유지나 독립 실행 환경 제한이 이점일 수 있다. 미래의 재사용 가능성이나 테스트 편의만으로 package를 만들지 않는다.

앱이 package를 소비하고 package는 소비 앱 source·전역 상태에 의존하지 않는다. 공개 API·호환성·빌드·검증 유지 비용도 고려한다. 개별 package 생성과 의존성 방향의 [architecture 경계](../architecture/overview.md#architecture-change)는 유지한다.
