# 개발 흐름

명확한 사용자 요청은 착수에 충분하다. 필요한 맥락을 읽고 구현, 검증, 관련 문서와 PR을 연속해서 완성한다. 별도 역할 선언이나 간단히 진행해도 되는 이유를 입증하는 절차는 없다.

## 요청과 작업 단위

사용자가 맡긴 응집된 결과를 단위로 삼는다. 화면·API·상태 처리·테스트가 함께 필요하면 같은 변경으로 완성한다. 파일, 테스트 사례, Red/Green 단계, 역할이나 줄 수로 PR을 나누지 않는다. 독립적으로 검토·출시·되돌릴 이유나 실제로 다른 범위가 있을 때만 분리한다.

테스트 자체의 결함 수정이나 검증 공백 해소가 목적이면 테스트 전용 PR도 유효하다. 기능 요청에서 테스트 준비만 끝낸 것을 기능 완료로 보고하지 않는다. 같은 결과의 내부 단계마다 사용자 merge를 기다리지 않는다. 별도 작업의 실제 선행 의존성과 안전한 통합에 필요한 merge는 구분한다.

장기 작업, 여러 세션의 인계나 협업에 상태 기록이 필요하면 같은 목적의 기존 Issue·PR 한 곳을 재사용한다. 현재 요구사항, 제약, 남은 작업과 필요한 근거면 충분하다. Execution Issue, preflight 댓글, roster, Worker ID, 모델 분류나 원문 복제는 의무가 아니다.

Discussion과 Project는 선택적인 제품 계획 도구다. 기존 계획·승인·완료 근거·실패·미완료 상태를 보존하며 카드 이동이나 Issue 생성으로 실행 권한이 생기지 않는다. 진행 작업을 재개할 때 기존 branch·결과·유효한 검증을 이어 쓰고, 필요하면 현재 기록 한 곳에서 폐기된 행정 조건만 정리한다. 기존 기록을 일괄 재작성·종료하거나 새 Issue에서 처음부터 다시 시작하지 않는다. 목표 완료는 카드나 자식 Issue 수가 아니라 약속한 결과로 판단한다.

## 판단과 권한

요청 범위 안의 되돌릴 수 있는 구현 선택은 담당자가 결정하고 필요한 이유를 결과에 짧게 남긴다. 함수·파일 분리, 테스트 위치, 기존 계약 안의 구현 방법마다 질문하지 않는다.

질문은 요청만으로 정할 수 없는 중요한 제품 동작, 기존 승인·금지와 충돌, 호환성을 깨는 변경, 보안·개인정보·데이터 손실·운영·비용 책임을 바꾸는 선택에 한정한다. 이유, 대안과 권장안을 제시하고 영향받는 부분만 보류한다. 요청 밖의 중요한 새 목적을 추가하지 않는다.

요청된 기능 안의 통상적인 dependency 선택은 기존 구현·표준 API·적합한 설치 패키지를 우선해 판단한다. 명시적 금지, 중요한 라이선스·비용·배포·보안 영향과 새 architecture 방향은 사용자 판단 경계다. 질문을 피하려고 범용 프로토콜·암호·경합 처리를 자체 구현하지 않는다. 필요한 재사용 판단은 [코드 재사용](code-reuse.md)을 따른다.

사용자가 요청하거나 실행을 허용한 Rule·architecture 변경은 필요한 구현·테스트·Reference와 하나의 검토 가능한 PR에 준비한다. PR에 채택할 실질적인 계약, status 변경과 적용 범위를 명시한다. 별도 승인 댓글이나 Rule-only 선행 PR은 필요 없으며 사용자 merge가 해당 변경의 승인과 활성화다. Merge 전에는 이 PR의 구현·검증 밖에 적용하지 않는다. Proposed 문서의 절차·링크 수정만으로 제품 설계를 채택하거나 status를 바꾸지 않는다.

제품별 구현 착수·실행 조건은 별도로 유지한다. 미확정 OS 지원, 실제 provider 등록, credential, 운영 DB·배포·비용·파괴적 작업, Windows 장애·복구의 실행 허용과 실제 검증은 절차 변경이나 문서 승인으로 충족되지 않는다. 실제 제품 계약 충돌은 해당 부분만 보류한다.

## 브랜치와 협업

작업 전 현재 checkout·remote·base·미commit 변경과 관련 진행 작업을 확인한다. 안전한 작업 브랜치가 기본이며, 이름은 목적을 알아볼 수 있으면 된다. Issue 번호나 workspace 접두어는 필수가 아니다. Issue 기반 준비가 편리할 때만 선택적인 [start-task](../../scripts/README.md#start-task)를 쓴다.

병렬 편집이나 미완료 변경을 격리할 때 worktree를 사용한다. 동시 editor는 같은 checkout을 공유하지 않는다. 다른 담당자의 종료·인계를 확인하지 않고 변경을 가져오거나 작업을 빼앗지 않는다. 기존 branch·worktree·미완료 결과를 무차별 reset·clean·stash·삭제하지 않는다.

별도 에이전트는 독립 작업의 전체 비용을 줄이거나 필요한 독립 검토를 제공할 때만 쓴다. 같은 탐색·구현을 경주시키지 않는다. 협업에는 맡은 범위, 기준 commit, 결과 위치와 공유 자원 소유권을 필요한 만큼 전달한다. 파일이 달라도 public contract, 생성물, port·DB·fixture의 충돌을 확인한다. 통합 담당자는 base 이후 의미 변화와 결과를 확인하고 요청 범위 안의 충돌을 해결하며 영향받는 검증을 수행한다.

모델 사용은 사용자의 현재 명시적 선택과 실제 실행 환경을 따른다. 사용할 수 없거나 확인하지 못한 설정·도구·에이전트를 사용했다고 보고하지 않는다.

## 실행과 검증

개발 중에는 수정 동작에 가까운 검사를, 마지막에는 최종 diff에 맞는 검증을 묶어 수행한다. [Testing](testing.md)의 영향·입력 기준으로 기존 성공 결과를 재사용하며 매 수정·commit·push마다 전체 검증을 반복하지 않는다.

실행과 monitor의 소유권을 명확히 한다. 실행 중인 명령은 같은 handle/job으로 확인하며 응답이 늦다고 새로 시작하지 않는다. 이벤트 기반 대기를 우선하고 변화 없는 polling과 로그 재독을 피한다. Shell 조회 성공, 일부 PASS나 취소 요청을 전체 job 종료·성공으로 바꾸지 않는다.

정상적인 수정과 관련 테스트 반복에 별도 배정이나 사람 판단을 요구하지 않는다. 원인·입력·가설 변화 없는 실패 반복, 담당자 교체를 통한 무한 재시도는 하지 않는다. 진전 없는 원인, 환경·권한 부재나 중요한 범위 선택이 드러나면 그 문제만 알린다. 외부 작업의 기존 timeout·비용·취소 안전 경계를 유지하고 남은 job과 실제 종료 상태를 구분한다.

## 리뷰와 전달

일반 작업은 담당자의 자체 검토가 기본이다. 인증·인가·보안, 데이터 손실·migration·복구, 중요한 동시성이나 되돌리기 어려운 의미 변경에는 실제 위험에 필요한 독립 검토를 붙인다. 파일 경로·Rule 분류·diff 크기만으로 독립 검토를 일률적으로 요구하거나 면제하지 않는다.

리뷰는 이번 변경이 도입하는 구체적인 correctness·security·reliability 문제와 중요한 계약 위반에 집중한다. 취향이나 근거 없는 가정으로 재리뷰를 반복하지 않으며, 심각도 표기만으로 중요한 결함을 무시하지 않는다. 지적을 한 번에 정리해 수정하고 영향받는 검사·재검토를 수행한다. 유효한 같은 head의 요청·결과는 재사용한다.

자동 리뷰는 필요한 때 `@ldb-review` 라벨로 요청할 수 있다. 모든 PR에 자동 부착하거나 모든 수정에 재요청하지 않는다. 라벨이 있는 PR의 후속 head에는 기존 자동화가 요청하므로 진행 중인 요청과 중복하지 않는다. 수동 요청 전에도 최신 head·기존 요청·자동 실행 상태를 확인한다. 자체 검토는 독립 리뷰가 아니며 요청 게시도 리뷰 통과가 아니다. 필요한 독립 검토를 받을 수 없으면 남은 조건으로 알린다.

관련 구현·테스트·문서를 같은 PR에 담고 commit은 이해에 도움이 되는 단위로 만든다. 별도 Red 커밋, 고정 커밋 순서나 줄 수 예산은 없다. PR은 실제 변경과 이유, 수행한 검증의 범위·결과, 미실행·실패와 남은 한계를 전달한다. 관련 기록은 링크로 연결하고 해당 없는 형식 항목을 채우지 않는다. 필요한 원격 CI·required check를 로컬 PASS로 대체하지 않는다.

사용자만 최종 merge한다. main 직접 commit·push, 자동 merge, branch protection·ruleset·권한·Secret의 임의 변경은 금지한다. PR 준비와 merge 완료를 구분하고, 미완료·실패·미검증을 성공으로 보고하지 않는다.
